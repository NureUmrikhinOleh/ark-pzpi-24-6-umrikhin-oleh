3 ОПИС ВИКОНАНОЇ РОБОТИ
     Під час виконання практичного завдання №2 на тему «Методи рефакторингу коду програмного забезпечення: Replace Temp with Query, Move Method, Pull Up Field» було обрано мою лабораторну роботу з минулого семестру — серверний Web API для бронювання номерів у готелях. Він написаний на C# з використанням ASP.NET Core та Entity Framework Core, дані зберігаються в базі SQLite. Проєкт невеликий: контролер бронювань BookingsController, клас DbSeeder для заповнення бази тестовими даними та п’ять моделей (Hotel, Room, Client, Service, Booking).
     Рефакторинг — це зміна внутрішньої структури програми, після якої код стає зрозумілішим і його простіше змінювати, але поведінка програми залишається такою ж. Методи обиралися з каталогу книги М. Фаулера [1] так, щоб вони не повторювались у групі і щоб вони були актуальними в власній роботі. Код до та після рефакторингу завантажено в репозиторій на GitHub у папки BeforeRefactoring та AfterRefactoring, а потрібні фрагменти наведено в Додатку В.
     3.1 Replace Temp with Query
     У методі CreateBooking контролера BookingsController перед створенням бронювання перевіряється, чи не зайнята кімната на вибрані дати. Результат запиту до бази записувався в тимчасову змінну isOccupied, яка використовувалась лише один раз — в умові if (див. Додаток В.1). Сама по собі змінна нічого не ламає, але через неї перевірка виявляється «прив’язаною» до одного методу. Якщо таку саму перевірку знадобиться зробити ще десь, наприклад при зміні дат бронювання, запит доведеться копіювати.
     Фаулер пропонує в такому випадку винести вираз в окремий метод, а звернення до змінної замінити викликом цього методу [1, с. 97]. Так і було зроблено: запит перенесено в приватний метод IsRoomOccupied, змінну прибрано, і тепер умова має вигляд if (await IsRoomOccupied(booking)) (див. Додаток В.2). Метод повертає Task<bool>, а await залишився в місці виклику, тому асинхронність початкового коду збереглася.
     3.2 Move Method
     У класі DbSeeder вартість бронювання рахувалася прямо на місці, і формула була написана двічі — окремо для кожного з двох бронювань (див. Додаток В.3). При цьому формула використовує тільки дані бронювання: дати заїзду та виїзду і вартість послуг. Виходить, що код лежить в одному класі, а працює з даними іншого. У книзі такий випадок названо «заздрістю до чужих даних» (Feature Envy) і рекомендовано перенести метод у клас, дані якого він використовує [1, с. 115].
     Розрахунок було перенесено в метод CalculateTotal класу Booking (див. Додаток В.4). Ціна за ніч передається параметром, а вартість послуг метод бере зі списку Services самого бронювання. У DbSeeder замість формул тепер стоять виклики booking1.CalculateTotal() та booking2.CalculateTotal() (див. Додаток В.5).
     Під час перенесення довелося поміняти порядок двох рядків. Раніше ціна послуги дописувалася у формулу вручну, а тепер береться зі списку, тому послугу треба додати в бронювання ще до розрахунку.
     Тепер формула записана один раз, а дані й поведінка, яка з ними працює, знаходяться в одному класі. Ціну послуг вже неможливо «забути» додати, а сам метод можна використати і в контролері, де при створенні бронювання сума поки що взагалі не рахується.
     3.3 Pull Up Field
     У всіх п’яти моделях (Hotel, Room, Client, Service, Booking) окремо оголошено однакову властивість public int Id { get; set; } (див. Додаток В.6). Це звичайне дублювання: якщо, наприклад, знадобиться змінити тип ключа на Guid, правити доведеться п’ять файлів.
     Метод Pull Up Field полягає в тому, що однакове поле з підкласів переносять у спільний батьківський клас [1, с. 259]. Батьківського класу в моделей не було, тому спочатку було створено абстрактний клас Entity, а вже потім у нього перенесено Id (див. Додаток В.7). Усі моделі тепер наслідуються від Entity, а рядок з Id з них видалено (приклад для класу Hotel наведено в Додатку В.8). Абстрактним зроблено саме клас, бо окремий об’єкт «сутність» без жодних даних не має сенсу. Властивість Id при цьому звичайна і зберігається в кожному об’єкті.
     Код, який звертається до Id (наприклад, booking.Id у контролері), змінювати не довелося, бо властивість успадковується. Клас Entity не зареєстрований у контексті бази даних як окрема таблиця, тому Entity Framework, як і раніше, додає стовпець Id до таблиці кожної моделі.
     3.4 Інструменти для рефакторингу
     Лабораторна робота виконувалась у VS Code з розширенням для C#. Доступні рефакторинги в ньому відкриваються через значок лампочки або комбінацію Ctrl+. (Quick Fix), окремо є команда Refactor (Ctrl+Shift+R) та перейменування F2, яке змінює назву в усіх файлах проєкту [2]. Для C# серед готових дій є, наприклад, Inline temporary variable, Introduce local variable та Move type to matching file [3].
     Inline temporary variable фактично виконує лише один крок Replace Temp with Query: якщо поставити курсор на змінну isOccupied, VS Code пропонує прибрати її і підставити вираз прямо в умову. Окремий метод-запит при цьому не створюється, тому IsRoomOccupied було виділено вручну. Move Method і Pull Up Field VS Code автоматично не виконує, тож їх теж було зроблено вручну, а після змін проєкт перевірявся командою dotnet build.


4 ВИСНОВКИ
     У результаті виконання практичного завдання на власному коді було застосовано три методи рефакторингу з книги М. Фаулера.
– За допомогою Replace Temp with Query тимчасову змінну isOccupied замінено методом-запитом IsRoomOccupied, тепер перевірку зайнятості кімнати можна використовувати повторно.
– Методом Move Method розрахунок вартості бронювання перенесено з DbSeeder у клас Booking, і формула тепер записана в одному місці замість двох.
– Pull Up Field прибрав дублювання властивості Id у п’яти моделях завдяки новому базовому класу Entity.
– На прикладі з порядком додавання послуги стало видно, що навіть простий рефакторинг може випадково змінити поведінку програми, тому після кожної зміни результат треба перевіряти.
– Отримано навички роботи з інструментами рефакторингу у VS Code і розуміння того, що середовище може зробити автоматично, а що доводиться робити вручну.
